# End-to-End Research Pipeline

`end_to_end_pipeline.ipynb` analyzes selected GitSkills families: it infers artifact relationships, compares direction-supported changes, detects security-sensitive indicators, and prepares samples for human validation. Indicators are review signals, not proof of malicious behavior or provenance.

## Run the notebook

1. From the repository root, install the project environment with `uv sync`. Open Jupyter with `uv run --with jupyterlab jupyter lab` and select the project environment as the kernel.
2. Prepare the DuckDB database using [data/README.md](../../data/README.md). It must contain `artifacts`, `artifact_groupings`, `artifact_siblings`, and `repos`.
3. Set `GITSKILLS_DB` to the database file, for example:

   ```bash
   export GITSKILLS_DB=/mnt/c/data/duckdb/agent_skills_release.db
   ```

   Without the variable, the notebook uses `C:\data\duckdb\agent_skills_release.db`.
4. Open `end_to_end_pipeline.ipynb`. In **Set Variables**, select the sprint and sample:

   ```python
   SPRINT = 2  # Sprint 2 or 3
   SAMPLE = 1  # For Sprint 3: 1, 2, or 3; ignored for Sprint 2
   ```

5. Sprint 2 requires its existing approved `samples/families.txt`. For Sprint 3, if `samplesX/families.txt` is missing, the notebook automatically generates 100 families and saves `families.txt` plus `sample.json` in that sample directory. Run samples 1, 2, then 3; later samples exclude names selected earlier. If the file exists, it is reused unchanged. You can also pre-generate lists with `family_picker`. One name per line; blank lines and `#` comments are ignored.
6. Check `POLICY`, `EDGES`, `PER_STRATUM`, `SEED`, and `APPROVAL_REFERENCE`. Sprint 3 uses `FAMILY_SAMPLE_SIZE = 100` and `FAMILY_SEED = SEED * 10 + SAMPLE` (5801, 5802, 5803) for family selection; `SEED = 580` separately controls manual-review sampling. Record the team's approval before setting `APPROVAL_REFERENCE`.
7. Run cells in order through **Findings for manual review**. Run the final adjudication cell only after the team's reviews are complete.

The notebook calls `summarize_cohort()` directly; separate `analyze_family`, `scan_family`, or `scan_diff` runs are unnecessary. By default, `EDGES = "primary"` scans selected predecessor relationships only. Pairs with ambiguous direction are considered for relationship validation, but not directed security comparisons. `PER_STRATUM = 5` selects up to five validation pairs **per category across the cohort**, without restricting the full analysis.

```text
    ├── results2/
    ├── samples3/                  # excludes all names in samples1 and samples2

```

`SPRINT` and `SAMPLE` select matching input and output folders automatically. For each run:

- **`samples/` or `samplesX/`** holds `families.txt`; Sprint 3 auto-generated samples also include `sample.json` with seed, policy, allocation, exclusion-file hashes, and validation statistics. Existing lists are never overwritten.
- **`results/` or `resultsX/`** holds every artifact generated by the notebook, including the *validation* samples and `sample_manifest.json`.
- **`.scans/`** holds family scan JSON files shared across runs. Cache entries are reused only when their source, database, rules, implementation, policy, and settings match; incompatible scans remain separate.

The selected `results` folder contains:

```text
resultsX/                            # Or sprint2/results/
├── sample_manifest.json             # Cohort inputs, provenance, checksums
├── execution_summary.json           # Execution and validation status
├── audit/                            # Processing and skipped-artifact records
├── review/                           # Pair-level data and research summaries
│   ├── summary.json
│   ├── families.csv
│   ├── directed_pairs.csv
│   ├── edge_types.csv
│   ├── direction_basis.csv
│   ├── indicator_frequency.csv
│   └── indicator_frequency_by_edge_type.csv
├── figures/                          # Generated SVG charts
└── manual-review/
    ├── directed-pairs/
    │   ├── validation_sample.csv
    │   └── annotations_template.csv
    ├── relationship-pairs/
    │   ├── relationship_validation_sample.csv
    │   └── relationship_annotations_template.csv
    └── adjudicated/                  # Team-created decisions
```

An automated `execution_summary.json` status of `complete` means processing finished; it does **not** mean human validation is complete. Sprint 3 selection requires at least one usable primary directed pair in every selected family; a changed policy, incomplete evidence, or an older pre-existing list may still affect actual results. Check the audit and coverage fields before interpreting their results.

## Human validation

See the [Manual Annotation Protocol](../../docs/instructions/manual_annotation_protocol.md) for field definitions, permitted judgments, and the full review procedure. Reviewers must inspect source content and relevant sibling files, not only scanner summaries. Do **not** execute scripts, installers, or commands stored in the dataset.

There are two independent review tasks:

| Task | Generated template under `RESULT_DIR/manual-review/` | Main questions |
|---|---|---|
| Directed changes | `directed-pairs/annotations_template.csv` | Are relatedness and direction supported? Were changed commands, file operations, network/credential evidence, and risk indicators detected correctly? Is coverage sufficient? |
| Relationships | `relationship-pairs/relationship_annotations_template.csv` | Are the artifacts related? Does the evidence support an inferred direction, if any? |

1. Verify the selected families and configuration in `RESULT_DIR/sample_manifest.json`. Preserve the generated sample CSVs and templates unchanged.
2. Give each reviewer separate copies of **both** templates. Keep the original row IDs and generated fields intact; fill only the manual review fields. Save as UTF-8 CSV.
3. Inspect raw `SKILL.md` content and relevant siblings using the IDs and repository paths in the manifest. The shared `.scans/` reports contain scanner observations; [SkillTrace](../../apps/skilltrace/) can help inspect source artifacts. The tool's inferred direction is not established ancestry.
4. Review independently, then resolve disagreements and save a team decision for every sampled pair. Use `uncertain` or `not_assessable` where the evidence does not support a stronger judgment. Preserve individual reviews.
5. Save the completed adjudicated files as:

   ```text
   RESULT_DIR/manual-review/adjudicated/directed.csv
   RESULT_DIR/manual-review/adjudicated/relationships.csv
   ```

   Use `review_phase=adjudicated`, `review_status=complete`, a reviewer ID, a date, and the required manual judgments for completed rows. The pipeline ignores pending rows in validation metrics.
6. Run the notebook's final **Independent review and adjudication** cell. It verifies the saved inputs and updates `review/summary.json` and `execution_summary.json` without rescanning when the evidence is compatible. Both adjudicated files must exist for this notebook cell to run.

For directed-pair indicator metrics, pairs must have supported relatedness and direction, complete evidence coverage, and a manual assessment of all eleven indicator categories. Metrics computed from review samples describe **sample accuracy**, not prevalence in the full dataset.

## Outputs and interpretation

The notebook writes research tables to `review/` and four SVG figures to `figures/`: `pair_outcomes.svg`, `indicators_by_family.svg`, `indicators_by_edge_type.svg`, and `indicator_frequency.svg`. These describe the full analyzed cohort, not just the manual-review subset.

When reporting results, distinguish supported indicators from uncertain indicators, direction-supported pairs from ambiguous relationships, and pair-level counts from independent security incidents. Multiple comparisons may share source artifacts. Missing sibling content or other incomplete coverage limits conclusions; a missing indicator is not proof of safety.
