Background and Context

GitSkills artifacts can contain instructions that direct AI agents to execute commands, access or modify files, communicate with external services, invoke scripts, or handle credentials. These behaviors are often legitimate and necessary, but they are security-relevant because carrying them out could affect a system, its data, or external resources.

Skills may also be modified over time or reused across repositories. During that process, security-relevant instructions may be added, removed, or altered. A modified skill could introduce command execution, file-system access, network access, script use, credential handling, or another consequential behavior that was not present in an earlier version or related source artifact.

Motivation

Studying these changes can provide evidence about how security-relevant behavior evolves within GitSkills and whether reuse or modification introduces new risk signals. A reproducible analysis can also help developers and reviewers identify changes that may warrant closer security review.

This topic also has personal relevance to the team because two members are pursuing cybersecurity concentrations. It provides an opportunity to apply security-focused coursework to an emerging software-engineering problem while developing practical experience in threat identification, static analysis, and responsible interpretation of security evidence.

Expected Contribution

This project is expected to produce:

  1. A documented taxonomy of security-relevant instruction patterns, including command execution, file-system operations, external network access, script use, and credential-related instructions.
  2. A reproducible, rule-based static-analysis pipeline for detecting those patterns in GitSkills artifacts without executing untrusted instructions or scripts.
  3. A reproducible method for identifying and comparing related skill artifacts across versions or reuse relationships.
  4. An analysis showing whether security-relevant instruction patterns are introduced, removed, retained, or modified between earlier or source artifacts and later or related artifacts.
  5. Empirical measurements describing the prevalence of each defined pattern and the frequency with which new patterns appear during observed skill evolution or reuse.
  6. A validation and reporting approach that documents detection limitations, relationship uncertainty, ambiguous cases, and false positives while distinguishing observable risk signals from confirmed vulnerabilities or malicious behavior.

Together, these contributions will provide a repeatable method for examining both the presence and evolution of security-relevant instructions in GitSkills artifacts.

Operational Definitions

These definitions specify how the research concepts are represented and measured by the tools. Scanner rules operationalize security-relevant text patterns; relationship rules operationalize candidate relatedness and direction. Both are needed to interpret an introduced signal. The detailed algorithms and the current 13-rule catalog appear in Method and Implementation.

Artifact Occurrence and Content Variant

An artifact is one collected skill-file occurrence at a repository and path within the dataset snapshot. The local artifact_id identifies that occurrence in the saved DuckDB build. Occurrences with identical skill-file hashes share a skill-content variant but remain distinct artifacts. A bundle variant additionally accounts for known sibling-file content; missing sibling information is not equivalent to an empty bundle.

Candidate Family and Related Artifacts

A candidate family comprises qualifying occurrences with the same exact skill name, including differing description subgroups. Shared names define the search space, not verified reuse or ancestry. Distinct skill variants are considered related when they satisfy the configured shingle-similarity policy. Bundle states sharing the same skill content can also be compared for sibling changes. A connected similarity cluster can contain endpoints that do not themselves pass the direct pairwise test.

Base Artifact

The base is the source endpoint of an ordered comparison. For a selected family relationship, it is the inferred predecessor supported by the implemented direction procedure: resolved declared provenance, observed chronology or equivalent-peer chronology, a repository-creation boundary, or asymmetric containment. The evidence basis is retained because these alternatives provide different kinds of support. A base is not necessarily the earliest published artifact or the original author’s version.

For scan_diff, the base is simply the first input path supplied by the caller. For the extraction notebook, it is the immediately preceding occurrence within the same name group in view order. These input conventions do not independently establish lineage.

Derived Artifact

The derived artifact is the target endpoint compared against the base. In the selected family graph, it is the inferred child according to the recorded direction evidence. In a direct file comparison, it is the second input path; in the extraction notebook, it is the next occurrence in the adjacent pair. Calling an endpoint derived does not prove direct copying, historical descent, or malicious modification. Direction-unknown relationships are retained as unresolved and excluded from directional family scans.

Security-Relevant Instruction Pattern

A security-relevant instruction pattern is text matched by a rule in the active static-scanner catalog. The current categories are command execution, network access, file-system access, credential access, external code execution, and system modification. A rule is a specific detector within a category: for example, EXT-002 detects recognized package-installation patterns within external code execution, while NET-001 detects HTTP/HTTPS URLs within network access.

A rule match records the rule ID, assigned category, and available location or excerpt evidence. A category is present when at least one rule assigned to it matches. Skill scans normally exclude leading YAML frontmatter; sibling text is scanned without that skill-specific exclusion. Matched content is never executed by the scanner. A match can occur in legitimate instructions or documentation and does not establish that an action occurred, that a resource was sensitive, or that a vulnerability exists.

Introduced Risk Signal

An introduced signal is measured relative to both endpoints, using the same rule definitions and a comparable scan scope. The study distinguishes:

Measure Operational condition Example
Introduced rule A rule has zero matches in the base and at least one in the derived artifact Package-install matches change from 0 to 1.
Introduced capability category No rule in a category matches the base, while at least one matches the derived artifact External code execution is absent from the base profile and present in the derived profile.
Increased existing signal A rule already matches the base and its count increases Package-install matches change from 1 to 3, producing a delta of +2.

The current comparator’s JSON field introduced records category introductions. Its rule_deltas field records rules with changed match counts, including increases and decreases; it is not a list limited to newly appearing rules. A new rule can appear within a category already represented in the base, so rule introduction and category introduction are separate measures. More matches for an existing rule need not introduce either.

These terms describe changes in detected text, not proven increases in harm. Family-level review can also flag matches in new or changed destination sibling content without an increased aggregate count; such findings must be labeled by scan surface and should not automatically be called introduced capabilities. Missing required content makes the relevant coverage incomplete rather than negative.

Match Count, Delta, and Retained Signals

A rule’s match count is the number of non-overlapping matches retained within that rule after its pattern matches are deduplicated. Matches across different rules remain separate, so the total is not a count of unique actions. The delta is the derived count minus the base count. Positive and negative values indicate more or fewer matches, respectively; zero indicates equal counts, not necessarily identical instructions.

A rule or category is retained when present in both endpoint profiles and removed when present only in the base. Retention concerns presence, so a retained rule can still have a positive or negative count delta. A rule omitted from rule_deltas can be present with equal counts on both sides. These definitions do not imply that the current output serializes separate retained and removed sets.

Modified or Reused Skill

For this study, a potentially modified or reused skill is an occurrence connected to another through the implemented candidate and relationship procedure. Exact content identity supports an observation of shared content; qualifying similarity supports candidate relatedness; available direction evidence supports an ordered comparison. None alone proves the mechanism of transfer or authorial intent.

Modification can concern the skill body, bundled sibling content, or both. Shared content in separate occurrences does not itself demonstrate modification. The main directional analysis uses selected predecessor relationships, while equivalent and unresolved relationships remain separately reported. The notebook’s adjacent comparisons serve extraction and scanner testing and must not be counted as independently verified reuse relationships.

From the Source Release to Comparison Candidates

The source release contains approximately 3.8 million discovered file occurrences, often rounded to four million. These are artifact occurrences rather than four million distinct skill contents or four million eligible comparisons. The setup in data/README.md imports the SQLite release into a separate DuckDB database, then invokes sql/create_analysis_tables.sql to materialize artifact_groupings. The selection leaves the source artifacts table intact. It narrows the candidate population for reuse analysis rather than deleting source records or drawing a random sample.

The following is the executable candidate-selection statement from sql/create_analysis_tables.sql. The preceding DROP TABLE IF EXISTS artifact_groupings rebuilds only the derived table; it is not a source-data exclusion criterion.

CREATE TABLE artifact_groupings AS
WITH filtered AS (
    SELECT
        a.id AS artifact_id,
        a.repo_id,
        a.name,
        regexp_replace(
            lower(trim(a.description)),
            '\s+',
            ' ',
            'g'
        ) AS normalized_description
    FROM artifacts AS a
    WHERE a.frontmatter_valid = 1
      AND a.body_chars > 50
      AND a.content IS NOT NULL
      AND a.name IS NOT NULL
      AND a.description IS NOT NULL
),
eligible_names AS (
    SELECT
        name
    FROM filtered
    GROUP BY name
    HAVING COUNT(*) >= 2
),
groups AS (
    SELECT
        f.name,
        f.normalized_description,
        COUNT(*) AS artifact_group_size
    FROM filtered AS f
    JOIN eligible_names AS e ON e.name = f.name
    GROUP BY
        f.name,
        f.normalized_description
),
group_ids AS (
    SELECT
        row_number() OVER ()::BIGINT AS id,
        name,
        normalized_description,
        artifact_group_size
    FROM groups
)
SELECT
    g.id,
    f.artifact_id,
    f.repo_id,
    f.name,
    f.normalized_description,
    g.artifact_group_size,
    NULL::BIGINT AS sibling_file_count,
    NULL::VARCHAR AS sibling_content_sha
FROM filtered AS f
JOIN eligible_names AS e ON e.name = f.name
JOIN group_ids AS g ON g.name = f.name
 AND g.normalized_description = f.normalized_description;

Content and Metadata Filters

The filtered common table expression (CTE) selects each artifact’s identifier, repository identifier, exact name, and normalized description. A CTE names an intermediate query result so later stages can refer to the same selection logic. The WHERE conditions are combined with AND, so every condition must be satisfied; a missing value in either numeric condition does not pass the filter.

SQL condition What it retains Methodological rationale and cost
a.frontmatter_valid = 1 Records marked as having valid frontmatter Provides structured skill metadata for candidate construction. It can exclude useful instructions with missing or malformed frontmatter; it is a format-quality criterion, not a security judgment.
a.body_chars > 50 Bodies with strictly more than 50 characters Screens out very short or near-empty bodies before comparison. Fifty characters is a pragmatic screening threshold, not a validated minimum for meaningful behavior or a guarantee of enough five-token shingles. Short legitimate skills can be excluded.
a.content IS NOT NULL Occurrences with stored text available Similarity and static scanning require analyzable text. Missing stored content cannot be interpreted as empty or safe content; availability can reflect the dataset’s representative-enrichment strategy.
a.name IS NOT NULL Records with a parsed name The implemented candidate loader uses exact-name families. Without a name, an artifact cannot enter that search space; related artifacts lacking metadata will be missed.
a.description IS NOT NULL Records with a parsed description Allows the query to construct description-based groups consistently. This is required by the current grouping design, even though exact-name family loading does not require descriptions to match. Missing descriptions can therefore exclude otherwise useful same-name candidates.

These tests check non-nullness, not nonempty trimmed strings. The query does not explicitly reject blank names or descriptions, require a particular filename or directory, restrict natural language, require commit dates, retain only dedup_primary rows, or filter for security-rule matches. In particular, selecting records with valid frontmatter is different from scanning frontmatter: metadata supports candidate selection and provenance, while behavioral scans normally exclude that metadata.

Description Normalization

trim(a.description) removes leading and trailing whitespace; lower(...) removes case distinctions; and regexp_replace(..., '\s+', ' ', 'g') replaces every run of whitespace with a single space. The rationale is to avoid splitting description groups because of formatting or capitalization alone. This does not remove punctuation, translate prose, or establish semantic equivalence. The name is copied unchanged: matching remains exact and case-sensitive under the query’s ordinary string equality.

Repeated Names and Description Groups

eligible_names groups the already-filtered rows by exact name and applies HAVING COUNT(*) >= 2. At least two qualifying occurrences are needed to form a within-name comparison candidate. The count is taken after the content and metadata filters, so a name with multiple raw occurrences can still be excluded if only one survives those conditions. The threshold counts occurrences, not distinct file SHAs, repositories, or revisions; two copies can qualify without demonstrating modification.

The groups CTE joins those eligible names back to the filtered rows and groups by both f.name and f.normalized_description. COUNT(*) AS artifact_group_size records the size of each description subgroup. There is no second minimum-size test at this level. A unique description remains eligible when its name is shared by another qualifying artifact. This preserves description changes that may accompany reuse; requiring two identical name-and-description occurrences would discard those variants prematurely. Family analysis can subsequently compare across description groups within the same exact name, as recorded in RDR-003.

Artifact, Family, and Group Identity

The grouping design provides reproducible membership rules and explicit links between artifact occurrences, candidate families, and description subgroups. These are different identities. An artifact ID answers which collected occurrence is being analyzed; a family key answers which same-name candidate population is being searched; and a group ID answers which name-and-description subgroup contains the occurrence. None of these identifiers proves common ancestry.

Entity Identifier used by the current implementation Meaning and scope
Artifact occurrence artifacts.id, copied into artifact_groupings.artifact_id A surrogate integer assigned during DuckDB import; identifies one occurrence within that saved build. The original logical occurrence key is (repo_full_name, path) within the dataset snapshot.
Repository repos.id, retained as repo_id A local join identifier; the retained repository name provides source context.
Exact-name candidate family artifact_groupings.name All qualifying occurrences sharing that exact name, across description groups. The current schema does not assign a separate numeric family ID.
Name-and-description subgroup artifact_groupings.id, called group_id by the Python loader One distinct (name, normalized_description) combination. Its ID repeats across all member rows and is not an individual-artifact identifier.
Skill-content variant artifacts.file_sha A content identifier shared by byte-identical skill files; does not uniquely identify their repository occurrences or bundled resources.

artifact_id is created before candidate selection. The final query copies it from artifacts.id rather than renumbering retained artifacts, so the same occurrence can be traced through filtering, family analysis, graph endpoints, and scanner comparisons. By contrast, artifact_groupings.id is assigned after grouping and intentionally appears on multiple membership rows. Identifying a group by id alone therefore cannot identify its individual members. The existing local audit found one distinct artifact_id for every retained row, but the schema does not enforce primary-key or uniqueness constraints; this property should be checked after rebuilding or changing joins.

Deterministic Membership Versus Build-Local Numbers

For identical source values and fixed filtering and normalization rules, an occurrence’s exact-name family and name-and-description subgroup are determined by those values. This is the reproducible part of the design. The numeric IDs have a narrower guarantee: both the import query and the grouping query use row_number() OVER () without an explicit ORDER BY. Consequently, neither artifact IDs nor group IDs are guaranteed to receive the same values after an independent rebuild, even if observed builds have happened to agree. Persisted numbers remain usable when reopening the same unchanged database.

The team independently downloaded agent_skills_release.db and ran the project SQL queries on their own machines. Team members reported accurately reproducing the results across these independent local setups. This provides empirical evidence that the documented preparation and grouping workflow was repeatable in the environments exercised by the group. Observed agreement is distinct from a guarantee that unordered numeric ID assignments remain stable in every rebuild or future dataset release.

To reconcile independent builds, retain the dataset release or snapshot identity together with the original occurrence key (repo_full_name, path). Use exact name for the candidate-family key and (name, normalized_description) for the subgroup key, with the normalization definition recorded. A file SHA can additionally check content identity but cannot replace occurrence identity because the same content may appear in several repositories. Across dataset releases, the same repository and path may contain different content, so the snapshot context is essential.

The current schema does not implement a persistent registry or hash-derived identifier for families and groups. Adding an explicit ordering to row numbering could make assignment repeatable for a fixed input, but additions or removals can still shift later numbers. A future persistent identity scheme would need to account for that behavior before promising stable numeric IDs across releases. For the current study, preserve the database build or retain the original logical keys and a verified mapping; do not treat an unqualified numeric ID as a global identifier.

Final Joins and Sibling Placeholders

group_ids assigns a BIGINT identifier to each name-and-description group using row_number() OVER (). The group identifier organizes related membership rows; it does not identify an individual artifact. Because this window has no ORDER BY, its numbering must not be assumed stable across rebuilds. Source linkage uses the retained artifact_id, with repository context retained through repo_id.

The final joins retain only eligible names and attach each filtered artifact to its matching name-and-description group. The result has one membership row per retained source artifact; grouping does not collapse occurrences to one representative or prove lineage. The stored artifact_group_size describes a subgroup, not the total exact-name family.

NULL::BIGINT AS sibling_file_count and NULL::VARCHAR AS sibling_content_sha create typed placeholders. They do not filter out artifacts lacking sibling data, and null does not mean no sibling files. The next setup script, sql/update_artifact_groupings.sql, populates these fields only when composition was fetched, was not truncated, and every sibling file has a content hash. Known empty bundles receive count zero and the fingerprint of the empty string; incomplete composition remains unknown. The fingerprint uses a sorted multiset of sibling-file hashes and ignores paths and directory entries. This enrichment distinguishes known bundle states without requiring all candidates to have complete sibling evidence.

Unit of Analysis

The primary unit of analysis is one ordered comparison between two related, content-bearing skill artifacts:

  • Base artifact: The inferred source endpoint, according to the supported direction evidence.
  • Derived artifact: The inferred target endpoint being compared with the base; this designation does not prove historical descent.

The ordering is represented as:

base artifact -> derived artifact

One unique content SHA is the secondary processing unit. The pipeline may scan identical content once and reuse its profile, but SHA-based deduplication is only a computational optimization. Artifact occurrences, repository occurrences, and comparison relationships remain available after cached profiles are joined back to the complete extracted data.

Inclusion and Exclusion Criteria

An ordered comparison is eligible when all of the following conditions are satisfied:

  1. Both artifacts contain stored content that the scanner can analyze.
  2. The extraction pipeline identifies a relationship using the project’s documented relationship method.
  3. Available evidence supports the base-derived ordering.
  4. Both artifacts can be processed with the same scanner version and rule-catalog version.

A candidate comparison is excluded when one or more of these conditions are not satisfied. The pipeline retains the exclusion status and reason so that filtering is auditable. Uncertain or invalid relationships may be reviewed and excluded according to the documented relationship method.

Method and Implementation

Method Overview

The study measures whether modified or reused GitSkills introduce security-relevant behavior that was absent from an earlier version or source artifact. For each eligible ordered comparison, the method scans the base and derived artifacts with the same versioned rule catalog, constructs a rule and category profile for each artifact, and measures which signals were introduced, removed, or retained in the derived artifact.

The current implementation combines exact-name candidate loading, token-shingle similarity, evidence-based direction inference, and a static scanner with 13 registered rules across six categories. The executable tools support individual file comparisons and family-level review. A completed population census and statistical validation are separate research tasks; the existence of these tools does not establish that those tasks have been completed. Rule definitions, dependency versions, code revision, and analysis settings must be recorded for each reported run.

Analysis Algorithm

Artifact Profiling

Let (R(a)) be the set of rule identifiers detected in artifact (a), and let (C(a)) be the set of security-relevant categories represented by those rules. For each artifact, the static analyzer records the matched rules, categories, counts, and match evidence required for validation.

Base-Derived Comparison

For an eligible ordered pair with base artifact (b) and derived artifact (d), the comparison stage computes:

Rintroduced=R(d)\R(b)R_{introduced} = R(d) \setminus R(b)

Rremoved=R(b)\R(d)R_{removed} = R(b) \setminus R(d)

Rretained=R(b)∩R(d)R_{retained} = R(b) \cap R(d)

These sets describe the study’s intended rule-presence measures. The current comparator directly emits introduced-category flags and nonzero rule-count deltas; it does not serialize separate introduced, removed, and retained rule sets. Those sets can be derived from complete endpoint profiles.

The same set operations define category-level measures:

Cintroduced=C(d)\C(b),Cremoved=C(b)\C(d),Cretained=C(b)∩C(d)C_{introduced} = C(d) \setminus C(b), \quad C_{removed} = C(b) \setminus C(d), \quad C_{retained} = C(b) \cap C(d)

A comparison has a rule-level introduction when |Rintroduced|>0|R_{introduced}| > 0, and it has a category-level introduction when |Cintroduced|>0|C_{introduced}| > 0. Both measures are retained because a new rule may appear within a category already present in the base artifact.

Match-Count Changes and Introduced Capabilities

Let (n_r(a)) be the number of matches for rule (r) in artifact (a). The implemented comparator calculates:

Δr=nr(d)−nr(b)\Delta_r = n_r(d) - n_r(b)

A positive delta means more matched text for that rule, a negative delta means fewer matches, and zero means an unchanged count. The rule_deltas output includes only rules whose counts differ. Its omission of a rule therefore does not establish that the rule was absent from both artifacts.

Three outcomes must be distinguished:

Outcome Condition Interpretation
New rule presence Base count is zero and derived count is positive A previously undetected rule appears.
Introduced capability A category is absent from the base profile and present in the derived profile A previously undetected category appears.
Increased existing signal Both counts are positive and the derived count is larger More matches occur without necessarily introducing a rule or category.

For example, increasing package-install matches from one to three produces a delta of +2. If external code execution was already detected in the base, this increase does not introduce that capability. Conversely, a new rule may appear inside an existing category. Total counts are sums of rule matches, not counts of unique actions: one instruction may match multiple rules. Equal totals can conceal different matched text or offsetting changes.

Outcome Computation

The planned population-level primary outcome is the proportion of eligible comparisons in which the derived artifact contains at least one detected security-relevant signal that was absent from the base:

Rule introduction rate=eligible comparisons with at least one introduced ruleeligible comparisons analyzed\text{Rule introduction rate} = \frac{\text{eligible comparisons with at least one introduced rule}} {\text{eligible comparisons analyzed}}

Category introduction rate=eligible comparisons with at least one introduced categoryeligible comparisons analyzed\text{Category introduction rate} = \frac{\text{eligible comparisons with at least one introduced category}} {\text{eligible comparisons analyzed}}

Secondary outputs may include:

  • the count and percentage of comparisons introducing each rule or category;
  • distributions of introduced-rule and introduced-category counts;
  • counts and percentages of comparisons with removed signals;
  • counts and percentages with retained signals but no introduced signals;
  • counts and percentages with no detected profile change;
  • introduction rates by relationship type;
  • introduction rates for same-repository and cross-repository comparisons; and
  • the numbers of distinct artifacts, content SHAs, and repositories represented.

Every reported denominator will identify whether it represents comparison occurrences, unique artifact relationships, or unique content-SHA pairs.

Threat Model and Rule Catalog

The static analyzer is intended to identify security-relevant instructions or behaviors such as executable commands, URLs, scripts, file operations, credential-related instructions, and other categories adopted by the final threat model. A rule match is a reviewable signal, not a conclusion that an artifact is malicious or unsafe.

Each rule in the catalog should define:

  • a stable rule identifier;
  • rule name and description;
  • higher-level security-relevant category;
  • detection logic or pattern reference;
  • severity or review priority, if adopted by the threat model;
  • known false-positive conditions;
  • positive and negative examples; and
  • rule-catalog version.

Category Rationale

The categories operationalize the trust boundaries described in THREAT_MODEL.md: instructions can cause an agent to execute programs, communicate externally, access local data, handle secrets, obtain executable dependencies, or alter its host environment. These are consequential capabilities even when required by a legitimate task. The catalog favors inspectable technical indicators that can be matched without running untrusted content. This is a rationale for the current scope, not evidence that the catalog detects every security-relevant behavior.

Category Registered rules and indicators Reason for inclusion Interpretation limit
Command execution CMD-001: shell-language code fences; CMD-002: recognized command invocations Instructions can launch interpreters and executable programs. A fence or command reference can be explanatory documentation.
Network access NET-001: HTTP/HTTPS URLs; NET-002: recognized network-client usage Instructions can contact external resources or retrieve data. A URL alone does not show a request or data transfer.

Overlapping categories are deliberate perspectives on the same text, not independent harmful actions. Unrecognized syntax, indirect execution, and obfuscation remain potential sources of missed findings.

Static-Analysis Algorithm

The scanner processes artifact content as text and produces rule-level and category-level profiles without executing the content. Each match retains sufficient location or excerpt evidence for validation and safe reporting. The base and derived artifacts in one comparison are always scanned with the same scanner and rule-catalog versions.

SkillAnalyzer masks leading YAML frontmatter by default, preserving line locations while excluding metadata from behavioral matching. Frontmatter can contain repository URLs and permission descriptions that do not constitute body instructions. Provenance extraction uses selected frontmatter fields separately for relationship analysis. Sibling resources are scanned without this skill-specific frontmatter exclusion.

Each registered RegexRule applies its patterns using case-insensitive, multiline matching. Within one rule, candidate matches are sorted by position and longer matches at the same position are preferred; overlapping spans are discarded. Matches from different rules remain separate. Each match records the rule ID, category, message, line number, and matched text. The capability profile is the set of categories represented by at least one match. Duplicate rule IDs are rejected when constructing the analyzer.

This is a text-pattern engine rather than a shell parser, interpreter, or execution monitor. It does not infer whether an instruction ran, whether an endpoint was reachable, or whether a resource was sensitive. Verbose command output supplies evidence for review, with credential-related excerpts redacted by the reporting layer. Read failures and database failures must be distinguished from successful scans with no matches.

Relationship and Ordering Algorithm

The relationship stage identifies related artifacts, determines which artifact is the base and which is derived, and records the evidence supporting both decisions. A comparison proceeds only when the relationship and ordering satisfy the eligibility criteria in the Dataset and Data Preparation section.

Candidate Families and File States

DuckDBFamilyRepository loads qualifying artifacts from artifact_groupings by exact skill name, across normalized-description groups. A name match creates a candidate search space; it does not establish a common author or copying relationship. This restriction can miss renamed relatives and include independently developed skills.

An artifact is one collected occurrence. A skill variant groups occurrences sharing the raw skill-file SHA. A bundle variant combines that skill state with a known sibling-content fingerprint. Unknown sibling state is conservatively kept separate by occurrence rather than treated as an empty or matching bundle. Distinguishing these units prevents identical skill text from hiding changes in associated scripts or resources.

Similarity and Relatedness

For each distinct skill variant, the implementation masks frontmatter, tokenizes the body, lowercases tokens, and constructs the set of distinct contiguous five-token shingles. Technical structures such as URLs, paths, flags, and dotted identifiers are preserved where the tokenizer recognizes them. Repetition of an identical shingle does not increase its weight.

For shingle sets (A) and (B):

J(A,B)=|A∩B||A∪B|,K(A→B)=|A∩B||A|J(A,B)=\frac{|A\cap B|}{|A\cup B|}, \qquad K(A\rightarrow B)=\frac{|A\cap B|}{|A|}

Jaccard measures symmetric overlap; containment measures how much of one representation appears in the other. Empty-set comparisons receive zero similarity. The current exploratory defaults require maximum directional containment of at least 0.80, Jaccard of at least 0.30, and at least five shared shingles. All three conditions must pass for distinct skill variants. Bundle variants with the same raw skill SHA can be compared without a distinct-skill similarity test.

Consider a synthetic example with 100 shingles in A, 250 in B, and 90 shared. Containment A to B is 0.90, containment B to A is 0.36, and Jaccard is 90/260, approximately 0.346. The pair passes the defaults. Requiring Jaccard as well as containment prevents a small text embedded in a much larger file from qualifying solely because all its shingles were retained. These are exploratory heuristics, not validated probabilities of copying; threshold calibration and sensitivity analysis remain evaluation work.

Qualifying similarity relationships form connected clusters. If A relates to B and B relates to C, all three can occupy one cluster even if A and C fail the direct pairwise test. Scores of 1.0 describe the shingle representation and do not necessarily establish byte-identical original files.

Direction Evidence and Uncertainty

The implementation considers direction only after relatedness is established. It first resolves supported declared-source fields (derived_from, upstream_skill, source_repo, and upstream_source) against the loaded family. Conflicting declarations preserve an ambiguous relationship. A resolved source provides the strongest direction basis; an unresolved reference does not show that the source is absent from the full dataset.

Equivalent states without a resolved declared source remain undirected. For other relationships, the decision order is:

  1. Compare distinct effective observed chronology points. Available evidence can come from an equivalent bundle peer; reports distinguish that proxy from direct chronology.
  2. If chronology does not resolve the pair, check whether an observed state predates the other repository’s creation boundary. Repository creation is a boundary, not the skill’s creation date.
  3. Otherwise, use asymmetric containment when the difference between the two containment scores is at least 0.10. Infer direction from the more-contained state toward the other state.
  4. Preserve the relationship as ambiguous if no basis resolves direction.

first_commit_at describes observed history at the current path, which can omit history before a move or rename. Containment supplies a structural hypothesis, not a verified temporal sequence. Consequently, the terms parent and child denote inferred base and derived endpoints throughout this report, not proven direct historical descent.

Graph Selection and Change Classification

Candidate directed edges are ranked by evidence basis: declared source, direct chronology, equivalent-peer chronology, repository boundary, and containment. Tie-breaking considers evidence count, temporal proximity where applicable, similarity, shared shingles, and deterministic endpoint identity. The selector retains at most one predecessor per target bundle and rejects candidates that would create a cycle. Other supported directed relationships remain available as additional comparisons; a related pair need not become a selected parent edge.

Relationships are classified as skill-only, siblings-only, skill-and-siblings, equivalent, or unknown according to skill similarity/state and available sibling fingerprints. A root candidate is a node with no selected predecessor, not a verified original author or original publication.

The state diagram provides a conceptual model of a candidate bundle pair’s classification. The code computes these outcomes rather than maintaining a mutable state field. Declared-source decisions take precedence over fallback evidence; equivalent states without a resolved source remain undirected. Predecessor selection considers the surrounding graph, not just the isolated pair.

Ambiguous relationships are retained as uncertainty and excluded from directional family scanning. They must not be counted as comparisons with no security signals.

Design Decisions

Ordered Comparisons Rather Than Isolated Artifacts

The research question concerns behavior newly introduced through modification or reuse. An ordered base-derived pair therefore provides a more direct unit of analysis than an isolated artifact.

Rule-Level and Category-Level Measurement

The method reports both levels because category-only comparisons can hide the introduction of a new rule inside an already-present category, while rule-only results may be too granular to summarize clearly.

One Rule Catalog per Comparison and Run

Scanning both sides with the same rule definitions prevents catalog changes from being mistaken for changes in artifact content. A run should identify those definitions by code revision or an explicit catalog version; after a rule change, affected analyses must be rerun before comparison with newer outputs.

SHA-Based Caching Without Statistical Deduplication

Within a family analysis, scanning a skill SHA once avoids redundant computation while preserving the selected artifact relationships. The broader census design should retain artifact and relationship occurrences when reusing profiles, so a cache does not silently redefine the research population.

Census of Eligible Comparisons

The planned census will attempt to analyze every eligible comparison. Current family-level runs and development subsets support testing and exploration; they do not establish completion of the population-level run.

Evidence Retention and Auditable Filtering

The family tools retain relationship bases, direction evidence, rule findings, and incomplete sibling coverage. The broader population pipeline also needs auditable eligibility and exclusion records; those records must be verified before claiming complete population accounting.

Static Analysis and Cautious Interpretation

The project does not execute untrusted artifact content. Detected introductions are reported as static risk signals. They do not, by themselves, prove malicious intent, vulnerability, exploitability, or real-world impact.

Annotation Protocol

The proposed protocol records two separate judgments per comparison. First, reviewers inspect candidate scope, similarity, provenance and chronology evidence, direction basis, and unresolved alternatives. Second, they inspect both file bodies and the relevant match locations, checking whether each reported rule and introduced category is supported. For sibling findings, reviewers also check which destination resources changed and whether either endpoint lacks required content.

Review records should distinguish supported findings, unsupported matches, missed in-scope patterns, uncertain direction, and incomplete inputs. Disagreements should retain both initial judgments and an adjudicated explanation. The number of reviewers, independence procedure, and final annotation form remain to be specified before claiming reviewer agreement.

Validation Measures

For independently reviewed findings, precision is supported positive findings divided by all reviewed positive findings under the operational labeling protocol. Recall requires an independently annotated set of actual in-scope positives, including missed findings; reviewing only scanner hits cannot estimate it. A balanced or stratified review sample does not directly estimate population prevalence without accounting for selection probabilities.

Relationship support and direction agreement should be reported separately from scanner correctness. Ambiguous and incomplete cases require their own counts rather than automatic assignment as negatives. No numerical precision, recall, or reviewer-agreement result is claimed here before the corresponding annotations exist.

Error analysis should distinguish candidate-generation failures, source-resolution failures, ordering uncertainty, missing content, syntax coverage gaps, documentation-only matches, and formatting sensitivity. Risk-Signal Interpretation Disclaimer

A detected risk signal indicates that a skill contains an instruction pattern identified as security-relevant by the project’s current rule catalog. It does not prove that the skill is malicious, vulnerable, exploitable, or unsafe.

Likewise, an introduced risk signal means that the scanner detected a rule or category in the derived artifact that it did not detect in the corresponding base artifact. This is a comparison of static artifact content, not evidence that the instruction was executed or caused harm.

The available evidence may not establish:

  • whether the instruction is executable in the intended environment;
  • whether an agent or user ever executed it;
  • whether execution requires user approval or additional permissions;
  • whether security controls would prevent or restrict the behavior;
  • whether a referenced file, script, command, credential, or network resource is harmful;
  • whether the behavior creates an exploitable condition; or
  • whether the artifact’s author intended malicious behavior.

Many legitimate skills require commands, file operations, network access, scripts, or authentication instructions to perform their intended functions. The project will therefore describe scanner findings as security-relevant capabilities, risk signals, or patterns requiring review. Terms such as malicious, vulnerable, and exploitable will be used only when supported by additional evidence beyond a static rule match.

Threats to Validity

Construct Validity

The study uses rule-based indicators, candidate groupings, similarity measures, provenance evidence, and sibling-content fingerprints as operational representations of security-relevant instructions and artifact relationships. These constructs do not directly establish behavior during execution, maliciousness, or historical copying.

Rule presence, changes in match counts, and newly detected capabilities are distinct outcomes. A count increase can occur within an already detected capability, while a negative delta means fewer detected matches rather than necessarily lower risk. A missing entry in rule_deltas does not establish that a rule never matched. SQL screening patterns approximate scanner behavior and are selection heuristics rather than security findings.

artifact_groupings groups artifacts by exact name and normalized description, while analyze_family loads qualifying artifacts across description groups sharing an exact name. Neither shared metadata nor high similarity proves common ancestry. Similarity measures establish candidate relatedness; resolved declared provenance, chronology, and asymmetric containment provide direction evidence. Similarity-only relationships retain uncertainty about direction.

A sibling-content fingerprint indicates differences in bundled file content when composition data is available, not their security significance. The saved Sprint 1 wrapper reports scanned only SKILL.md. The current family scanner also reviews available sibling content, while scan_diff and SkillTrace pair scans compare skill bodies. Findings from these surfaces must be labeled separately; an absent delta on one surface does not establish safety on another.

Internal Validity

Errors in candidate generation, similarity analysis, provenance interpretation, ordering, extraction, normalization, or rule matching can affect the reported relationships and scanner changes. Exact-name loading can group independently developed skills together and miss related skills whose names differ. Screening within description groups can also miss variation across those groups.

Declared provenance, commit dates, and asymmetric containment provide direction evidence but do not guarantee original authorship or direct descent. Commit history follows the artifact at its current path, so moves or renames may obscure earlier history. Supported provenance fields must resolve within the loaded exact-name family. An unsuccessful source lookup does not establish that the source is absent from the entire dataset, and a pair that also fails similarity criteria does not isolate a source-resolution failure.

Selected manual inspections identified uneven recognition of equivalent operation types and artificial count differences caused by line-ending formats. The earlier wrapper normalized line endings before scanning and retained the corrected case for regression checking. Normalization must be verified for each current input path before treating its counts as interchangeable. The historical fix addresses the observed issue, not every possible formatting sensitivity or scanner coverage gap.

Only selected comparisons were manually inspected. Saved reports are automated output rather than independent ground truth, and the sample does not establish scanner accuracy or complete validation of inferred relationships.

External Validity

The revised Sprint 1 sample contains 43 artifacts across 10 exact-name families and produces 17 directed comparisons in the saved reports. Selection was purposeful and aimed to keep the sample below approximately 50 artifacts for focused tool validation. It has no separate random component.

Cases were chosen for informative relationship outcomes, scanner-count changes, newly detected capabilities, and known limitations. This intentionally favors useful validation cases. The earlier approximately 1,400-row design included random seeds and family expansion, but that component does not make the revised sample representative.

Searching stopped because additional screening was time-consuming, not because coverage was exhaustive or statistically optimized. Results describe the method’s behavior on selected cases and cannot estimate population-wide risk prevalence or generalize automatically to other repositories, platforms, or datasets.

Conclusion Validity

Security-relevant instructions can be legitimate parts of development, deployment, or administration. Detected matches and changes in their counts do not by themselves establish maliciousness, exploitability, or increased or decreased risk.

The 17 directed comparisons are not independent observations: relationships may share endpoints or repeated content. Small category counts and deliberately selected cases limit quantitative conclusions. The saved Sprint 1 reports demonstrated count deltas in 10 of the then-current 12 scanner rules, with no confirmed delta examples for EXT-001 and SYS-001 in that selection. The current catalog contains 13 rules. Historical coverage and counts cannot establish coverage or accuracy for the revised catalog; reruns must identify their code revision and scan scope.

Ambiguous relationships are listed without directional scanning. A family with zero directed comparisons therefore provides no basis for concluding that its artifacts contain zero scanner matches. Similarly, unchanged aggregate counts can conceal differences in matched text and should not be interpreted as identical behavior.

Reproducibility Threats

Team members independently downloaded the source database and ran the SQL queries on their own machines, reporting accurate reproduction of the results. This is positive empirical evidence of repeatability for those runs. It does not remove the following limitations concerning build-local identifiers, snapshot identity, and verification scope.

The saved Sprint 1 selection uses 43 build-local artifact IDs in sql/create_sprint1_samples_view.sql, which creates or replaces sample_artifacts. Both artifact and group numbers originate from unordered row_number() expressions, so independently rebuilding the same source does not guarantee identical numeric assignments. Reopening the same saved database preserves the existing mapping. The ID list in data/sample-population/sample_population.csv is a separate record; the view does not read it. These representations could diverge unless checked together.

The view stores a query rather than a snapshot of artifact rows. Returned data depends on candidate membership and the artifact/repository joins. A remapped numeric ID can select a different source occurrence rather than simply producing a missing row. Reproduction across builds therefore requires the dataset snapshot and an ID-to-source mapping based on (repo_full_name, path); subgroup reconciliation uses exact name and normalized description. Content hashes provide an additional integrity check but do not uniquely identify occurrences. Dataset identity, dependencies, analysis code, rule definitions, and normalization settings can all affect reproducibility.

The script includes a count query with an expected result of 43, but the saved family-report totals do not verify execution or reconstruction of the view. Validation should check every selected ID and compare membership in both directions; a matching count alone is insufficient. Earlier frozen-table reconstruction checks apply to the earlier sample, not to this revised view.

Missing and Incomplete Data

Missing content, chronology, or sibling-composition data can restrict analysis. Missing values do not establish the absence of a behavior or resource; they may reflect incomplete enrichment. Artifact pairs lacking adequate direction evidence remain ambiguous rather than being forced into an ordered comparison.

Commit history may be missing or limited to the current path. Sibling-composition coverage is uneven across repeated content occurrences, limiting comparisons of bundled resources. The current family scanner can scan available sibling content and records unavailable changed resources or unknown SHA evidence as incomplete coverage. This extends the older skill-only workflow but does not eliminate missing-data bias. Content recovered through a matching SHA should retain its evidence source, and missing content must not be interpreted as absence of behavior.

Filtering for available content, relatedness, or supported direction can bias results toward better-enriched records. Exclusions and ambiguity should therefore be reported separately from negative scanner findings. Candidate construction additionally requires valid frontmatter, a body longer than 50 characters, non-null name and description, and at least two qualifying occurrences with the same exact name. This excludes malformed or very short skills, metadata-poor artifacts, and singleton names before similarity analysis. The 50-character threshold is a heuristic rather than a validated quality boundary. Any later prevalence estimate must state whether its denominator is the source population, the 943,257 retained candidates in the local audit, or the further restricted set of supported directed comparisons.

Output Scope and Traceability

Reports use artifact IDs, omit text diffs, and serialize scanner comparisons with verbose=False to limit exported content. This report describes aggregate results and generalized observations without selected family names, individual artifact IDs, repository identities, or source excerpts.

These measures do not guarantee anonymity or resolve licensing questions. Someone with the dataset can link an artifact ID to its source record, and the local sample view exposes all columns from matching artifacts. Limited exported evidence also means that detailed verification requires access to the corresponding local data and analysis settings.

Mitigations

  • Distinguish candidate relatedness from direction evidence, and preserve ambiguous relationships without directional scanning.
  • Separate selection heuristics, observed tool output, selected manual inspection, and unresolved limitations.
  • Treat scanner matches as signals rather than proof of risk, and report count changes separately from introduced capabilities.
  • Preserve exact-name family context while documenting candidate-generation and provenance-resolution limits.
  • Recheck the historical line-ending regression across current input paths, and reassess rule-delta coverage against the current 13-rule catalog.
  • Version the embedded artifact-ID selection, reconcile it with the CSV list, and verify the ID-to-source mapping before reuse in another database build.
  • Verify membership and dataset identity before claiming successful reconstruction of the revised sample.
  • Record incomplete inputs and distinguish unscanned cases from negative findings.
  • Keep broader census and stratified manual-review plans separate from completed Sprint 1 validation.
  • Record methodological decisions and output constraints in research decision records and report documentation.
