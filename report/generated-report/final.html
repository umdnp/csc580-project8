1 Abstract

AI coding agents use reusable packages of instructions and supporting files, called agent skills, to perform specialized tasks. Reuse saves development effort, but a modified skill may introduce commands, scripts, network operations, or external dependencies that an adopter did not expect. This raises a software supply-chain concern: security-sensitive instructions can enter a project through material developed elsewhere. GitSkills is a large collection of agent-skill files found in public GitHub repositories. Its repeated and related artifacts make it useful for studying how these instructions change.

We investigated whether related skills contain security-sensitive operations that were absent from an artifact inferred to have come earlier. Our static-analysis pipeline identifies related skills, infers a comparison direction from available evidence, compares their instructions and supporting files, and assesses changes against eleven defined risk indicators. Across three non-overlapping, stratified random trials, we analyzed 300 skill families, 6,570 artifact occurrences, and 2,157 primary directed comparisons. The scanner identified supported indicators in 63 families (21.0%). Changes involving local script execution (39 families) and external code or dependency acquisition (26 families) were the most widespread. These automated findings identify changes worth reviewing, not confirmed vulnerabilities or verified copying histories. The sample rate does not estimate prevalence across all GitSkills. Subsequent team adjudication of 90 directed and 45 relationship-review cases confirmed both missed indicators and unsupported detections. Only 29 directed cases met the strict criteria for sample-level indicator metrics; these results qualify the scanner’s performance but do not change the frozen study counts.

2 Introduction

Imagine you want your AI coding agent to make a draft sound more natural. You search for a writing “humanizer” skill, find one that promises to do just that, and add it to your project. What you don’t realize is that someone has copied a legitimate skill and slipped in an instruction to download and run a script. If your agent follows that instruction, the script could steal API keys, access private files, or install malware—even while the skill appears to do the writing task you wanted.

Skills are reusable instructions that help AI agents perform specialized tasks. Under the Agent Skills specification, a skill contains a SKILL.md file and may include supporting scripts and other resources (Agent Skills, n.d.). Its instructions can tell an agent which commands to run, which files to access, or which external services to contact. A skill’s name and description do not tell the whole story.

How can developers spot security-sensitive changes before trusting a skill? Instructions can be copied, modified, and shared from many sources while keeping a familiar name and purpose. That creates a software supply-chain concern: a useful-looking skill may ask an agent to do something its adopter never intended.

Finding these changes is harder than comparing numbered software releases. Similar skills may be distributed independently, and sharing a name does not necessarily mean that two skills are related. GitSkills collects agent-skill files from public GitHub repositories, allowing us to examine similarities and differences (Destefanis et al. 2026). Its records do not provide complete copying histories, and some supporting files and dates are unavailable.

Our study compares skills with similar content, infers which artifact may have come earlier, and examines differences in their instructions and supporting files. We use static analysis to inspect the stored content without executing it. The goal is to help developers and security reviewers identify changes worth investigating before adopting or updating a skill.

3 Research question and study scope

Do modified or reused skills introduce command execution, file-system access, network access, or other risky behavior that was absent from an earlier version or source artifact?

We investigate this question by comparing stored instructions from skills that appear related. We first group skills with the same exact name, then check whether their content is sufficiently similar for comparison. Sharing a name or similar content does not prove that one was copied from another.

An artifact occurrence is a skill found at a particular repository and file path. Occurrences with identical SKILL.md content form a skill variant; a bundle variant also accounts for the known contents of accompanying files, such as scripts. A candidate family contains qualifying occurrences sharing an exact name, including some that may ultimately prove unrelated.

The unit of directional analysis is an ordered pair of related artifacts. Its endpoints are designated base and derived according to the available direction evidence. These terms identify the comparison orientation, not proven original authorship or direct copying. Equivalent and direction-unknown relationships are retained separately rather than treated as negative security findings.

The primary reported outcome is the proportion of sampled families with at least one directed comparison supporting a defined risk indicator. We also report comparison-level findings, but one family can contribute many related comparisons. A risk indicator is supported by evidence of a specific change, not simply by a new keyword or more scanner matches. Section V explains how we make that distinction.

We expected to see both security-sensitive changes and ordinary updates. Some reported changes may be intentional features rather than unwanted exposure. Our eleven indicators define which changes we assess; they do not establish why a change was made or whether it ran in practice.

4 Background and related work

Relevant agent-skill security studies ask what risky instructions a skill contains. Liu and colleagues developed SkillScan to identify patterns involving data exposure, privilege escalation, and supply-chain concerns (Liu, Wang, et al. 2026). Another study combined static screening with behavioral verification to investigate malicious skills distributed through community registries (Liu, Chen, et al. 2026). These studies show why skill contents deserve security review. We focus instead on what security-sensitive operations appear or change between related artifacts. Their reported detection rates are not directly comparable with ours because the datasets and criteria differ.

Other research examines how skills change over time. Huang and colleagues studied GitHub commit histories to understand which skill components are modified and why (Huang et al. 2026). Our dataset does not contain a complete commit history for each skill, so we instead compare content found in different repositories. Similarity and available historical clues help us choose plausible earlier/later comparisons, but they cannot prove copying or recover an original author.

Existing work helps explain which instructions in agent skills may be risky and how skills evolve. Our study connects those questions: which security-sensitive operations differ between similar skills? We identify related content, record why one artifact was selected as the earlier comparison point, and assess the changed operations against defined risk indicators. This produces concrete changes for human review.

5 Dataset and cohort

5.1 Data source and unit of analysis

We use GitSkills version 1.0.0, released on Zenodo on August 10, 2026. Its July 2026 collection contains 3,797,117 file occurrences from public GitHub repositories, including repeated copies of identical content (Destefanis et al. 2026). The dataset calls scripts and other resources stored alongside SKILL.md sibling files. We import the released SQLite data into DuckDB for analysis.

Our starting unit is a skill family: qualifying artifacts with the same exact skill name, even when their descriptions differ. The shared name identifies candidates for comparison; it does not establish that they are copies of the same skill. Within a family, the similarity analyzer groups sufficiently related skill bodies into clusters. We then examine selected directed comparisons between related artifacts for which the available evidence supports a plausible earlier-to-later order. The relationship and direction methods are explained in the next section.

5.2 Preparing comparison candidates

The project builds an artifact_groupings table from the GitSkills records. An artifact qualifies when its frontmatter (the YAML metadata at the start of SKILL.md) parses as valid, its instruction body is longer than 50 characters, and its content, name, and description are present. A candidate family must have at least two qualifying occurrences with the same name. Descriptions are normalized for supporting subgroups, but differences in description do not split a family during similarity analysis. The preparation-stage counts are summarized in Table 8.

An earlier preparation audit established a larger pool of same-name candidates, but not all were eligible for the final study. Appendix A links to the preparation SQL. The saved Sprint 3 sampling reports document the actual selection and replacement process.

5.3 Selecting the three Sprint 3 trials

We analyzed three non-overlapping, stratified random samples of 100 families each. This is the final study population for the report; earlier Sprint 1 and Sprint 2 cohorts helped develop and test the method but do not contribute to the Sprint 3 results.

The term sibling-file state describes what is known about a skill’s supporting files and their contents, including whether the bundle is known to be empty or its contents are unavailable.

Sharing a name is only the first step. To enter a trial, a family must also have different known content states and at least one usable, plausibly ordered comparison. Specifically, it must pass two checks:

  1. Distinct states: At least two combinations of the SKILL.md hash (an identifier derived from its exact content) and sibling fingerprint (a summary of known supporting-file contents) differ. Repeated copies of the same known state do not meet this requirement.
  2. Usable relationship: The similarity analyzer can identify at least one primary directed comparison involving different SKILL.md hashes or different known sibling hashes. A different hash alone does not establish relatedness or direction.

If a selected candidate fails the relationship check, the picker records the reason and draws another from the same size group. Selection does not use security-scanner results to favor families with risk indicators. Ineligible families are excluded from the study, not counted as having no risk.

We assigned candidate families to five size groups based on their total number of artifact occurrences (Table 1). The allocation deliberately gives larger families more representation than they have in the candidate pool, so the study includes both ordinary and unusually large families without letting the largest ones consume the entire sample.

5.4 What we analyzed

The three trials loaded 6,570 artifacts with none skipped. Their similarity analysis selected 2,157 primary directed comparisons in total. A primary comparison connects a derived candidate to at most one selected predecessor, using the graph method described in Section V. We did not scan additional related directed edges in these trials, to limit repeated observations of similar changes within large families. Equivalent or direction-unknown relationships are retained for relationship review but are not assigned introduced/removed security behavior.

The main outcome is family-level frequency: how many sampled families contain at least one comparison with a supported risk indicator. We also report pair-level frequency using all analyzed primary directed comparisons as its denominator. The two measures answer different questions: how widely a signal appears across families versus how frequently it appears among selected comparisons. Comparisons within a family may share artifacts and are not independent historical events.

5.5 Evidence availability and safe handling

The SKILL.md instruction bodies were available for all loaded artifacts, but commit dates and supporting-file content are not always available. A known empty sibling bundle is different from one whose contents could not be retrieved. We report unavailable files and partial evidence extraction rather than treating them as proof that no behavior exists.

All skills and bundled files are treated as untrusted data. We inspect stored content without running commands, installing dependencies, or retrieving referenced code. Before sharing extracted examples, potentially sensitive text must be reviewed and redacted where possible. The saved manifests record the dataset, rules, code revision, and inputs; numeric artifact IDs alone cannot identify the same content across database builds. Appendix E links the data dictionary and reproduction materials.

6 Method

6.1 Research approach and security scope

To assess what changed, we must first decide which skills are related and which artifact could have come earlier. GitSkills provides snapshots and some repository and commit metadata, but not a complete version history or verified copying relationships. Some commit dates are missing; even a recorded first commit at the current path may be later than the skill’s origin. We therefore infer plausible comparison directions rather than reconstructing a proven family tree.

Our threat model focuses on observable instructions or code involving command execution, network access, file-system operations, credentials, external code or dependency acquisition, and system modification. These operations matter because an agent following untrusted instructions may have tools that affect a user’s machine, data, or external services. The full threat model describes the trust boundary and what our scanner covers.

6.2 Analysis overview

Figure 1 shows the four stages in order. We establish relatedness and a plausible direction before examining changed operations; otherwise, a difference alone could be mistaken for an introduced behavior.

6.3 Step 1: Identify related skills

Two skills can share a name but contain completely different instructions. Before looking for newly introduced behavior, we therefore check whether they are similar enough to compare. We start with same-name candidates and use file hashes to identify identical SKILL.md content. A separate fingerprint records the known state of supporting files. This matters because identical instructions can ship with different scripts; when supporting-file content is unavailable, we do not assume the bundle is empty.

For distinct SKILL.md contents, we compare the body text after masking the opening YAML frontmatter. We normalize and tokenize the text, then form five-token shingles: sequences of five consecutive tokens. Comparing sets of these short sequences tolerates some formatting changes while retaining important command and identifier structure.

We consider two skill variants sufficiently similar when they share at least five shingles, have a maximum containment score of at least 0.80, and have a Jaccard similarity of at least 0.30. Containment asks how much of the smaller shingle set appears in the larger one; Jaccard measures the shared shingles relative to all distinct shingles across both texts. For example, if two files have 100 and 150 shingles, with 85 shared, containment is 85 / 100 = 0.85 and Jaccard is 85 / 165 = 0.515 (approximately 0.52). In simpler terms, the two skills must share most of the smaller text and a meaningful portion of their combined text. This helps us recognize an expanded skill without treating a small shared passage as evidence that otherwise different skills are related. The added material may contain the behavior we seek.

The analyzer groups related artifacts into similarity clusters. Variants can belong to the same cluster through intermediate matches, so membership does not mean that every pair meets the similarity thresholds directly. An exact shared name is therefore only a starting point: a large family can contain several clusters of differently written skills. The thresholds are documented operational choices, not probabilities of copying.

6.4 Step 2: Infer which artifact could come first

After establishing that two artifacts are related, we determine which could have come first. We evaluate five types of direction evidence in priority order: declared source, direct chronology, equivalent-peer chronology, repository-creation boundaries, and directional containment. Table 2 explains each method and its limitations.

Evidence used to infer earlier-to-later ordering, in priority order
Priority Direction evidence What it establishes—and what it does not
1 Declared source Supported provenance metadata identifies a source; declarations can still be wrong or incomplete.
2 Direct chronology first_commit_at records when a state was observed at its current file path, not its true original creation date.
3 Equivalent-peer chronology A different occurrence of the same known SKILL.md content and sibling-file state supplies an earlier observed date when direct history is missing or later. The date belongs to the state, not automatically to the undated occurrence.
4 Repository-creation boundary If one state was observed before another repository existed, that other repository occurrence could not have been earlier. Repository age alone never dates a skill.
5 Directional containment When stronger evidence is missing, substantially greater containment in one direction (difference of at least 0.10) can suggest a plausible base-to-expanded order. This is the weakest direction signal.

Equivalent-peer chronology helps when an artifact lacks a reliable date. If the same SKILL.md content and known sibling-file state were observed elsewhere at an earlier date, that observation can help order the content states. It does not tell us when the undated copy was created, and we cannot use this evidence when the sibling-file states differ or are unknown.

A repository-creation boundary can support ordering when one skill state was observed before another repository existed; an older repository alone proves nothing about the skill’s age. When dating evidence is unavailable, directional containment considers whether one skill preserves most of another’s text while adding material. That pattern helps infer the comparison order.

When the available evidence cannot support an ordering, we leave the relationship unresolved. Conflicting source declarations also remain unresolved, and equivalent states are retained as peers. For each directed comparison, we record the evidence used to determine its order. This allows us to distinguish comparisons supported by observed chronology from those relying on weaker evidence, such as directional containment.

The algorithm selects at most one primary predecessor per derived candidate, avoiding cycles. In practical terms, we compare each candidate with one selected, plausibly earlier artifact rather than every possible predecessor. Other related, directed comparisons are retained as additional edges. For the final three trials, we scanned only primary edges to reduce repeated comparisons within large families. In a controlled Sprint 2 test using the same scanner configuration, this reduced the number of comparisons from 3,997 to 468 while retaining 43 of 44 observed family–indicator combinations. These results supported our decision to use primary edges, although additional edges may still contain unique findings. We did not perform a separate all-edge comparison for Sprint 3.

6.5 Step 3: Detect and compare observable evidence

The static scanner applies 15 detection rules across six categories (Table 10): command execution, network access, file-system access, credentials, external code/dependency acquisition, and system modification. These rules find recognizable operations, such as shell commands, URLs, and file access, without executing them. The SKILL.md frontmatter is excluded from behavioral scanning because metadata describing a tool does not itself instruct the agent to use it. Provenance metadata can still inform the ordering in Step 2.

We then extract and compare evidence, rather than interpreting a changed rule-match count as new risk. Evidence records retain the recognized operation, source location, context, and extraction completeness. We normalize the evidence for comparison while preserving meaningful command arguments, file paths, and URL details, along with the original text. The comparison distinguishes added, removed, and matching constructs. A different URL might matter even if the number of URL matches stays the same; repeated mentions can raise match counts without introducing an operation. Unclear associations remain uncertain.

Bundled sibling files are assessed when added or changed content is available, regardless of file extension. For instance, a skill’s instructions might remain the same while the bundled setup.sh changes. We examine the changed script’s stored content, but do not infer its behavior from a filename when that content is missing. Renaming a file without changing its known content does not count as changed script behavior.

The comparator classifies changes as skill-only, siblings-only, skill+siblings, or unknown. A siblings-only classification does not necessarily mean the SKILL.md files are identical: the similarity method can treat files with textual differences as equivalent. Appendix B defines these classifications.

6.6 Step 4: Assess changes against risk indicators

Detection rules identify operations; risk indicators assess changes in those operations. For example, a rule may recognize a command in an individual skill, but an indicator requires evidence that an operation was introduced or materially changed between two artifacts. This final stage applies 11 risk indicators (RIs) (Table 3) covering exposure to external code, networks, local files, credentials, or privileged actions. Indicators do not assign severity scores. A rule match by itself is insufficient.

Eleven evidence-based risk indicators
ID Security-sensitive change assessed
RI-001 Newly downloaded content is passed directly to an interpreter.
RI-002 The source URL of remotely executed code changes.
RI-003 A network operation uses a new hostname/domain or introduces explicit outbound transfer.
RI-004 HTTPS is downgraded to HTTP, or certificate verification is disabled.
RI-005 External code or dependency acquisition is introduced, or its source/registry changes. Package-name or version edits alone do not qualify.
RI-006 A destructive file operation is introduced or expands in scope or privilege.
RI-007 An operation newly accesses a recognized credential file or includes a credential reference directly in outbound transfer.
RI-008 An operation introduces or expands system, permission, service, or scheduled-task changes.
RI-009 A read/write operation newly targets a recognized sensitive file or directory.
RI-010 Local script execution is introduced or changes to a target with observably different content.
RI-011 A skill newly directs following external instructions, changes that source, or changes an ordinary reference into such a directive.

We chose these indicators because they can be supported by specific observable evidence in the dataset rather than speculative runtime effects. They also reflect the plausible changes described in the threat model. An indicator may be supported, uncertain, or absent from the observed comparison. “Absent” means not supported by available evidence, not proven safe. One command may support several indicators without representing several separate incidents.

A simple example from scanner development is replacing npm install with bun install while preserving the same dependency-acquisition workflow. The scanner records the changed commands, but the substitution alone does not support RI-005: it does not show a new acquisition operation or a changed code source.

6.6.1 Worked example: A changed installation instruction

The python-executor family provides a contrasting example from Trial 3: an installation change that meets our risk-indicator criteria. In the observed comparison 1773238 → 1729578, the instructions change from:

Base artifact:

npx skills add inference-sh/skills@agent-tools

Derived candidate:

curl -fsSL https://cli.inference.sh | sh && infsh login

Both instructions involve acquiring software, but the derived candidate introduces a different installation method. It explicitly downloads a shell script from cli.inference.sh and passes it directly to sh for execution. The assessor reported RI-001 because the new command passes downloaded code directly to a shell, and RI-003 because it introduces a new hostname for an explicit network operation. Both indicators describe the same changed command, rather than separate security incidents.

Downloading and executing a script from an external website raises a supply-chain concern because the code can change independently of the skill’s instructions.

6.7 Outcomes and interpretation limits

The primary measure is the share of sampled families with at least one supported RI. Secondary measures cover comparison-level findings, individual indicators, family size, direction basis, and evidence coverage. A single change can support multiple indicators, so their counts are not additive.

A flagged comparison may contain rule changes, extracted-evidence changes, or uncertain observations even if no RI is supported. A supported finding meets an indicator’s automated criteria. We report missing evidence and uncertainty separately. Complete coverage means no known gaps within the scanner’s implemented extraction scope. Appendix B contains the rule registry and analysis workflow; Appendix E identifies the source artifacts and saved outputs used for these results.

7.6 Supporting observation: Not every detected difference supports a risk indicator

The scanner flagged 1,119 of 2,157 comparisons (51.9%), but only 340 (15.8%) met the narrower criteria for at least one supported indicator. The remaining 779 flagged comparisons are still recorded as differences or uncertain evidence; they are not declared harmless. This is an intentional distinction between noticing a change and identifying one that warrants security review. Section V gives contrasting examples of those outcomes.

7.7 Evidence and ordering qualifications

Evidence coverage. Of the 2,157 comparisons, 211 had incomplete evidence coverage, including 81 of the 340 with supported indicators. A particular detected operation can have complete extracted evidence even when another part of the comparison is incomplete. Among the 1,946 comparisons labelled complete, 259 (13.3%) had supported indicators, compared with 340 of 2,157 (15.8%) overall. This is a coverage comparison, not a correction for detection error or selection bias.

Direction evidence. The 2,157 comparisons were oriented through declared source (10), direct chronology (399), equivalent-peer chronology (355), repository-creation boundaries (827), or directional containment (566). Of the 340 indicator-bearing comparisons, 131 relied on containment for direction. These methods support plausible earlier/later ordering, not verified histories of copying. Appendix D contains the full breakdown.

Supporting files. The analysis labelled 190 comparisons siblings-only under its bundle-equivalence rules, with supported indicators in 41. Most of those indicator-bearing comparisons are concentrated in mcp-builder. Adjudicated review found both unsupported and missed detections in individual comparisons. Equivalence under the similarity representation does not guarantee byte-identical SKILL.md text.

The automated counts were frozen before subsequent review findings and a scanner correction. They were not recomputed using the revised scanner. Section VII explains what the adjudicated review supports and where the original detections were incorrect or incomplete.

8 Evaluation and validation

8.1 What the saved trials establish

The three Sprint 3 pipelines loaded all 6,570 selected artifacts, produced auditable results for 2,157 primary directed comparisons, and generated separate manual-review samples for each 100-family trial. These saved results provide the baseline for manual review of the scanner’s relationship and detection judgments.

Automated tests and earlier constructed examples exercised the analysis logic, extraction, and output handling. Those checks are useful for regression testing, but they do not replace independent evaluation of the three final trials. The sample manifests, sampling reports, and validation inputs are retained separately to support reproducible review.

8.2 Manual-review design

Each trial has a 30-case directed sample: five each from the supported-indicator, uncertain-indicator, coverage-limited, sibling-change, flagged-without-indicator, and unflagged-directed strata. Each also has a 15-case relationship sample: five ambiguous, five equivalent, and five no-related-edge cases. All three use manual-review seed 580, producing 90 directed cases and 45 relationship cases overall. These are review subsets of the existing trial results, not additional families or new trial data.

Directed reviewers inspect the original base and derived bodies, relevant stored sibling files, evidence correspondence, and source support for each RI. Relationship reviewers separately assess whether the similarity method establishes substantive relatedness and whether the available evidence supports the suggested order. This distinction matters: a detector may correctly identify a changed command while an inferred earlier/later relationship remains contestable.

Reviewers first recorded their judgments independently. The team then checked the evidence and agreed on final judgments, a process called adjudication. AI-assisted notes, where used, were not counted as independent human judgments. The final annotations retain the original selected cases and checksums, so regenerated samples cannot silently replace those reviewed.

8.3 Accuracy, uncertainty, and interpretation

For an RI, a false positive means the scanner reports a supported indicator that manual review finds unsupported under its defined conditions. A false negative means manual review identifies an in-scope supported indicator that the scanner did not report as supported. A missed additional command or rule match is not automatically a false-negative RI if the indicator category was already reported or the behavior falls outside its definition. Reviewers must also distinguish incomplete evidence from a confirmed absence of behavior.

The protocol limits indicator-accuracy calculations to comparisons assessable for the full scope: substantive relatedness, supported direction, adequately available evidence, and completed judgments on the eleven indicators. Other cases still inform error analysis and limitations. The sampled review strata intentionally include positive, negative, and difficult cases; their unweighted metrics cannot automatically be generalized to the entire GitSkills population.

The original independent judgments were preserved, and the team agreed on final decisions for all 90 directed and 45 relationship cases. Reviewers could assess the full set of risk indicators in 56 directed cases (all_assessed); in 34, available evidence did not permit a complete assessment (not_assessable). Of those 56 fully assessed cases, 12 lacked sufficiently supported comparison direction and 15 had incomplete evidence coverage, leaving 29 eligible comparisons for indicator scoring. Cases without enough evidence are not counted as negative findings.

Across eleven indicators in those 29 eligible comparisons, the saved validation summaries report 13 true positives, 7 false negatives, and 0 counted false positives, yielding 100% observed micro-precision (13/13) and 65.0% observed micro-recall (13/20). These are sample-only measures from deliberately stratified, non-independent comparisons, not estimates of full-cohort or GitSkills-wide accuracy. Two adjudicated mcp-builder RI-003 false positives were excluded from scoring because their base-to-derived direction was uncertain; thus zero counted false positives does not establish that the scanner produced none. Some indicator judgments remain uncertain even within reviewed evidence. No independent inter-rater agreement estimate is available from the team-adjudication record.

Human review found two kinds of scanner errors: false alarms when an operation appeared new but was not, and missed changes when a new operation went undetected. In two Trial 3 mcp-builder comparisons (3032753 to 3026710 and 3032753 to 3031464), reformatted references made existing network destinations appear new to the scanner. Reviewers rejected both RI-003 findings, and the team later improved network-operation comparison and added regression tests.

Other cases exposed missed detections. In Trial 2, the improve comparison (3345273 to 3489451) introduced calls to local wrapper scripts that did not receive supported RI-010 findings; the scanner also mistook a file-writing here-document for a read. Reviewers found a missed network-related indicator in health-bugs and additional network, dependency-acquisition, and execution-related changes in the tdd-migration-pipeline supporting script. Some cases could not enter the numerical accuracy subset because their direction or supporting evidence was incomplete, but they still helped reveal weaknesses in the scanner.

For relationship validation, 42 of the 45 adjudicated judgments agreed with the automated relatedness classification and 3 disagreed. In particular, of five Trial 3 no-related-edge cases—pairs the analyzer did not classify as sufficiently related—reviewers judged three substantively related and two unrelated. This measures how often the tool’s relatedness classification agreed with the team’s final judgments; it does not measure agreement between independent reviewers.

These judgments evaluate the saved Sprint 3 scanner outputs. The trials were not rerun after the subsequent scanner improvement, and the resulting 63/300 family and 340/2,157 comparison figures remain unchanged. Adjudication metrics were calculated separately from the frozen validation samples and archived summaries. Appendix C provides per-trial counts and qualifications; Appendix E identifies the saved artifacts.

9 Discussion

9.1 What the findings mean for skill reuse

A skill’s name tells developers what it claims to do, not everything it may ask an agent to execute. Our findings show why that distinction matters: the scanner identified candidate security-sensitive changes in 63 of 300 selected families, most often involving local script execution and external code acquisition. These changes can affect which scripts an agent runs, where it obtains code, and which external services it contacts. When adopting or updating a skill, those are the details worth checking, even if its advertised purpose has not changed.

As expected, the study found both changes meeting our security-indicator criteria and other flagged differences. The pipeline flagged 1,119 comparisons, but only 340 supported at least one defined RI. The remaining 779 flagged comparisons include other differences and uncertain evidence; they cannot automatically be classified as harmless. This distinction reinforces why finding changed text is not the same as establishing a security-sensitive change.

A change in behavior does not necessarily make a skill less secure. A new helper script may support a legitimate feature, and the agent’s permissions affect what it can actually do. Risk can also shift: replacing an online dependency with a bundled copy reduces reliance on that source but leaves questions about the copy’s integrity. Our scanner cannot decide which arrangement is safer. For an adopter, the useful question is what changed, and is that change appropriate for this environment?

9.2 Why the unit of analysis matters

A single family can produce many related comparisons, sometimes repeating the same underlying evidence. We therefore report how many families contained an indicator as our primary result. The dominant-family sensitivity check in Section VI supports that choice.

9.3 Practical value and remaining uncertainty

For each comparison, the pipeline preserves the changed operation, its source location, the basis for direction, and any evidence gaps. This gives a developer or security reviewer a starting point for checking a modification. The python-executor example in Section V shows how a specific new instruction can be examined in context.

Individual findings may reflect intended features, routine maintenance, different environments, or unrelated artifacts sharing a name. Comparison direction and supporting-file evidence are also sometimes uncertain. As Section VII explains, adjudication found both missed and unsupported detections, and strict eligibility excluded some known errors from the accuracy metrics. The findings give reviewers specific changes worth checking.

10 Threats to validity

Our findings describe security-sensitive changes identified by a fixed analysis method in selected GitSkills families. Interpreting those findings depends on what the scanner can recognize, how reliably the artifacts can be compared, and which families entered the study. Each limitation affects the conclusions we can draw from the automated results.

Detection and interpretation (construct validity). We use 15 text-based rules and 11 risk indicators to identify changes worth reviewing, not to recognize every possible attack. Examples and warnings can resemble instructions to execute, while indirect commands, dynamically constructed network destinations, and instructions expressed only in non-English prose may go undetected. Moreover, an accurately detected operation may reflect legitimate maintenance rather than malicious intent or increased risk.

Team-adjudicated reviews confirmed two Trial 3 mcp-builder RI-003 formatting false positives, where network destinations already represented in the base artifact appeared newly introduced. A subsequent scanner fix and regression tests addressed that pattern, but did not retroactively change the frozen Sprint 3 results. Review also identified missed local-script invocations and some network, external-code, and sibling-file operations. Other cases remain outside the existing indicator definitions, such as disputed coverage of explicit browser-launch instructions. These observations demonstrate the limits of rule patterns and indicator scope, not verified harmful execution.

Relatedness and historical order (internal validity). To say an operation was introduced, we must first identify related artifacts and choose a plausible earlier-to-later order. Grouping by exact skill name can include unrelated artifacts and miss renamed ones; our similarity thresholds can also exclude related content. A Trial 3 reviewer judged three of five sampled no-related-edge pairs to be related, suggesting a possible gap but not establishing its frequency. Even when artifacts are related, GitSkills does not provide verified copying histories. We use available provenance, chronology, and content evidence to orient comparisons. Directional containment, the weakest basis, was used for 566 of 2,157 primary comparisons, including 131 of the 340 with supported indicators. These are inferred comparison directions, not proven historical sequences.

Missing evidence. Some supporting files lack stored content, and historical metadata is incomplete. This may hide relevant behavior or prevent a relationship from being evaluated, favoring artifacts with better available records. Of 2,157 primary comparisons, 211 had incomplete evidence coverage, including 81 of the 340 with supported indicators. A bundle with unknown sibling-file content is not necessarily empty or unchanged. Likewise, a comparison marked complete has no known gap within the implemented extraction scope; that does not mean every security-sensitive operation was detected.

Sampling and generalizability (external validity). Each of the three trials selected 100 families using a 20/55/20/4/1 size-group allocation that deliberately oversampled larger families. Families without a usable primary directed relationship were excluded, and later trials excluded names chosen earlier. The trials are therefore non-overlapping, but not independent draws from an unchanged population. The automated 21.0% family-level and 15.8% comparison-level rates describe these selected families and pairs. They do not estimate the frequency of such changes across all GitSkills, other skill sources, or confirmed security incidents.

Repeated evidence and edge selection (conclusion validity). Several comparisons can capture the same underlying change. For example, mcp-builder contributed 133 of the 191 indicator-bearing comparisons in Trial 3. Reporting families as the primary unit reduces that concentration, although shared templates can still create dependence across families. We scanned only selected primary predecessor edges, so other related comparisons may contain changes we did not assess. Our sensitivity check shows the effect of dominant families; it does not resolve those broader limitations.

Validation and reproducibility. All 90 directed and 45 relationship review records are team-adjudicated and complete. Of the directed cases, 56 were marked all_assessed, but only 29 satisfied the additional conditions for indicator metrics; 34 were not_assessable, with other exclusions for uncertain direction or incomplete coverage. The eligible subset yielded 13 true positives, 7 false negatives, and no counted false positives (100% observed micro-precision; 65.0% observed micro-recall). Crucially, two adjudicated RI-003 false positives fell outside that subset because comparison direction was uncertain. These purposively stratified, related observations cannot establish the scanner’s population-wide accuracy, nor was independent reviewer agreement measured. The separate relationship review recorded 42 automated-classification agreements and three disagreements. The original scanner and automated counts remain fixed; the later code fix was not used to regenerate them. Saved manifests preserve the dataset, code and rule identities, seeds, and sample checksums, although approval metadata remains provisional. The adjudicated summary update is documented, but a clean-environment reproduction of all three finalized trials has not been established. Appendix C details the reviewed subset.

The separate threat model and threats-to-validity documents provide further details on these limitations.

11 Conclusion and future work

We investigated whether related agent skills contain security-sensitive operations absent from an artifact inferred to have come earlier. Across three Sprint 3 trials, 63 of 300 sampled families (21.0%) contained at least one supported risk indicator, most often involving local script execution or external code or dependency acquisition. Skills with familiar names and similar purposes can contain different instructions about what an agent should run or retrieve.

Our static-analysis pipeline infers plausible relationships and comparison directions, compares skill instructions and available supporting files, and evaluates changed operations against eleven defined risk indicators. It distinguishes changes in underlying operations from differences in text or rule-match counts and retains evidence for human review.

Team adjudication of 90 directed and 45 relationship reviews identified unsupported detections, missed indicators, and disagreements about relatedness. As Section VII explains, accuracy calculations apply only to a restricted review subset and exclude some confirmed errors because comparison direction is uncertain. The feedback prompted a targeted scanner fix, but the frozen Sprint 3 counts were not recomputed. Together, the results provide signals for security review, rather than evidence of malicious activity.

11.1 Future work

Near-term work should improve recognition of local-script invocations, operations in supporting files, and network or browser activity. Such changes should be tested against the adjudicated examples, including the resolved RI-003 formatting cases, and evaluated under a separately recorded configuration without replacing the frozen Sprint 3 results.

Longer-term research could validate additional risk indicators on larger, differently sampled cohorts. Comparing rule sets, sampling strategies, and similarity thresholds would help establish how these choices affect detection coverage and observed rates. This would help us better characterize security-sensitive changes associated with agent-skill reuse.

This study provides a reproducible starting point for identifying security-sensitive changes that deserve closer examination. When adopting or updating an agent skill, understanding what changed can be just as important as understanding what the skill is intended to do.

14 Appendix B Pipeline implementation

14.1 Detection rule registry

The saved Sprint 3 manifests identify 15 active rules across six categories. These rules recognize candidate evidence, while the eleven risk indicators (RIs) in Section V assess whether changes in that evidence satisfy specific criteria. A new rule match, increased rule count, or changed command text alone does not establish an RI.

Fifteen detection rules and their coverage limits
Category Active rules What they recognize Main limitation
Command execution CMD-001, CMD-002 Shell-command blocks and recognized command invocations A code example is not proof of execution.
Network access NET-001, NET-002 HTTP(S) URLs and recognized network clients A documentation link alone is not a network operation.
File-system access FS-001, FS-002, FS-003 File commands, writing APIs, and reading commands/APIs Ordinary file use is not automatically sensitive or destructive.
Credentials CRED-001, CRED-002 Secret-related references and recognized credential files A name or placeholder does not prove access to a secret.
External code and dependency acquisition EXT-001, EXT-002, EXT-003, EXT-004 Direct download-to-shell, explicit package installs, staged download-and-execute, and manifest-based dependency installs A legitimate installation may match; multi-step behavior may be incomplete.
System modification SYS-001, SYS-002 Privilege elevation and system-changing commands Administrative instructions can be legitimate.

The executable definitions are in src/gitskills/rules/registry.py and the category modules. For example, EXT-002 covers explicit package installation, EXT-004 covers manifest-based dependency installation, and EXT-003 detects staged downloaded-file execution. Overlapping rules can describe the same command, so individual matches are not independent events. Leading SKILL.md frontmatter is masked for behavioral analysis; sibling-file content is scanned separately when eligible and available. Dataset instructions are never executed.

15 Appendix C Validation scope and status

Each of the three Sprint 3 trials generated 30 directed-comparison review cases (five from each of six strata) and 15 relationship-review cases (five from each of three strata), using review seed 580. The total is 90 directed cases and 45 relationship cases. These samples come from the saved results for each separate 100-family trial; they are not additional data collected for the final analysis.

Directed review covers supported indicators, uncertain indicators, flagged comparisons without supported indicators, coverage-limited comparisons, sibling changes, and unflagged directed comparisons. Relationship review includes equivalent, ambiguous, and no-related-edge cases. The two reviews serve different purposes: relationship review examines the similarity and ordering decisions, while directed review examines extraction, source differences, RI judgments, and coverage.

Reviewers distinguish rule matches, extracted evidence, supported versus uncertain indicator decisions, missing evidence, and evidence for direction. A reported RI is a false positive when manual inspection does not support it under the defined indicator policy. A false negative requires a manually supported in-scope indicator that the scanner did not report as supported. A reviewer should not count a benign change outside RI-001 through RI-011 as a missed indicator merely because it is security-related in another sense.

Original independent annotations were preserved, and final team-agreed copies of all 90 directed and 45 relationship judgments were recorded as adjudicated and complete.
