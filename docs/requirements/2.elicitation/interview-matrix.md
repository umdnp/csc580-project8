| **Q8: How should “other risky behavior” be operationally defined?** | NotebookLM proposed five operational categories: credential/secret handling; script bundling, creation, and dynamic invocation; file-system/system operations such as privilege changes or sensitive paths; data harvesting paired with outbound network activity; and supply-chain/cross-version risk inflation where later candidate variants add capabilities absent from an earlier observed candidate. | **Q9: Can static analysis distinguish benign operational permissions from unnecessary exposure or exfiltration?** | NotebookLM proposed several contextual heuristics: declared-versus-inferred capability mismatch, workspace-local versus sensitive/system paths, source-to-sink combinations such as credential reads followed by outbound network calls, and cross-version changes that add new capabilities. | **Q10: How can the scanner distinguish passive documentation examples from active instructions?** | NotebookLM proposed using Markdown AST/heading structure, fenced-code context, imperative-versus-descriptive language, proximity between trigger verbs and commands, optional tool declarations, and file location (`SKILL.md` versus auxiliary files) to add context to detections. | **Q11: Can matching `name` + normalized `description` with different `file_sha` values identify likely modified/reused skill families?** | NotebookLM agreed this is a practical high-precision candidate-generation strategy: require the same frontmatter `name` and normalized `description`, require distinct content hashes, then order candidates by `first_commit_at`. It also warned that description edits can cause false negatives, boilerplate descriptions can create false positives, and `first_commit_at` follows the file at its current path. | **Sources:**<br>• Project `DATA_DICTIONARY.md`<br>• GitSkills sample repository<br>• CSC 580 Group Project requirements PDF (RQ4)<br><br>**Note:** Different `file_sha` values establish different file contents, and the current-path limitation of `first_commit_at` is documented. A different SHA proves the contents differ, not that one is a modified copy of the other. The earliest `first_commit_at` should be called the earliest **observed** candidate, not the original source. | We need to manually inspect a sample of candidate families to estimate precision. If false positives are material, we should add a lightweight similarity check within candidate families rather than across the entire dataset. |
